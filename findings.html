Cortex — Findings

Scope: all numbers below come from one test repo (Social-Network-Backend, 15 JS files, Express/CommonJS) and one 20-question dataset (src/eval/dataset.json). Treat them as indicative for a small corpus, not general benchmarks. Answer *correctness* has not been measured yet (Phase 4C).

5. Findings

  1. Hybrid retrieval clearly wins. Recall 99% at both k, versus 80-83% (k=5) for vector-only. On structural questions hybrid reaches 100% recall@5 against 72% (naive) and 68% (ast).
  2. AST chunking did not beat naive chunking at file level on this corpus. At k=10, recall was 81% (ast) vs 96% (naive). AST creates many small chunks per file, so the top-k chunks cover fewer distinct files (3.0 vs 4.0 at k=5). AST did have the best precision at k=5 (54% vs 40%).
  3. The file-level metric cannot see AST chunking's actual purpose (not cutting a function in half inside a chunk). This result is not evidence that AST chunking is worse; answer quality (Phase 4C) is where its benefit should show if it exists.
  4. Hybrid's recall edge is partly structural. A graph document surfaces several files at once, so hybrid returns 6.8 distinct files at k=5 versus 3.0 for ast. Its precision and recall are not a like-for-like comparison with vector-only configs.
  5. Graph-only fails where it should. Zero hits on semantic questions s02, s04, s08 and on t08 (jwt.verify, a library call with no definition in the repo). Hybrid covers these via the vector path, which justifies the hybrid design.
  6. Ensemble weighting is untested. Hybrid used fixed 0.5/0.5 weights; no tuning was done.

Findings:

  1. Line-range headers plus explicit citation rules removed the wrong-file and wrong-line errors in this sample: 4 misattributions and 4 wrong line claims with the legacy prompt, none with the cited prompt. All 30 line citations in the cited answers are correct.
  2. Part of the gain is terseness. Cited answers are about 26% shorter, so there were fewer claims to get wrong; the cost shows up as an omission (t01 dropped one of five call sites) and thinner explanations.
  3. The automatic checker is only a floor. It caught 2 of the 5 wrong legacy line citations, because a line inside a retrieved range passes even when it is off by one, and it cannot see wrong file attributions or wrong details. It is still useful for confirming the cited prompt's citations.
  4. c01 failed under both prompts because of retrieval, not generation. The real createPost function was never retrieved; a comment-only chunk (// 2 - Create a Post) took its slot, and the model answered about comments or speculated. Prompting cannot fix missing context.
  5. Comment-only chunks are a measurable AST chunker problem: 14 of 64 AST chunks (22%) contain only a comment and 21 are under 60 characters (naive: 0). This likely explains part of AST's lower distinct-file coverage in section 4 and the c01 failure. Fix (not yet done): attach leading comments to the declaration that follows, then re-index and re-run the retrieval eval.
  6. Generation time. Legacy averaged 135s per answer and cited 288s, but the cited run overlapped with other work on the same CPU-only machine, so the difference is not a clean measurement of the prompt.

Caveats: 10 questions, one repo, one reviewer (the model assisting the user), one sample per question at default sampling temperature (individual answers vary run to run, e.g. an earlier CLI run of t01 dropped likeRoutes.js). Counts are directional, not statistically significant.

7. Earlier findings

Phase 2 — naive vs AST chunking (docs/phase2-chunking-comparison.md)

  • Inconclusive: the test repo was a single 35-line file, so retrieval never had to choose between chunks.
  • An early chunker only matched named functions/classes and silently fell back to one whole-file chunk for

inline Express callbacks; fixed by chunking at top-level-statement granularity.

  • Every file-path citation in the answers was hallucinated because chunk metadata never reached the

prompt; fixed by passing source into the document prompt.

Phase 3 — vector vs code graph (docs/phase3-hybrid-retrieval.md)

  • The graph retriever returns complete answers where vector-only misses files (e.g. "which route files

use protect": vector-only missed followRoutes.js and postRoutes.js; graph returned all 20 call sites).

  • Bug found and fixed: substring file matching made the token routes match every route file; now exact

path / basename matching.

  • Semantic questions return no graph documents, so the graph path stays out of the way.

8. Known limitations and observations

  • Generation quality (llama3.1:8b). Measured in section 6 on 10 answers. Beyond those results:

it dropped likeRoutes.js from a protect answer in an earlier CLI run even though it was in the retrieved context, and guessed file paths in Phase 2 before paths were passed to the prompt.

  • Name-based call graph. References are matched by name (foo() and a.b.foo() both record foo), so

same-named functions in different files are not distinguished; "imported by" matches on basename.

  • Graph file documents have no line ranges, so answers about a file's imports can only cite the file path.
  • Graph retriever loads every code_graph row for the repo on each query; fine at 407 rows.
  • Dataset size and bias. 20 questions over one 15-file repo, written by reading the code with the

retrieval design in mind (mitigated by hand verification against the source with grep).

  • t06 ("which files import the User model") expects 11 files, so recall@5 is capped near 45% by design.

9. Not yet measured

  • The effect of fixing comment-only AST chunks on the retrieval eval and on c01.
  • Larger or multi-language repos.
  • Alternative ensemble weights, smaller/faster generation models.
